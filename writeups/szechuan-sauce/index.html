Reconstructing a Windows Data Breach: The Case of the Stolen Szechuan Sauce

A solo digital forensics investigation of DFIR Madness Case 001: how disk images, event logs, registry hives and a packet capture piece together an RDP intrusion, malware persistence, lateral movement and data theft across two Windows machines.

By Bill Lo · October 30, 2026

A secret Szechuan sauce recipe has turned up on the dark web. The victim’s network is two Windows machines, a domain controller and a desktop. The job is to find out whether there was a breach, how the attacker got in, what they did and what they took.

This is The Case of the Stolen Szechuan Sauce, a free forensics challenge created by James Smith of DFIR Madness. I investigated it on my own as the final project for CST8806 Digital Forensics at Algonquin College. This article walks through what I found and how I found it.

The case and the evidence

The victim network had two hosts on the 10.42.85.0/24 subnet:

SystemIP addressOperating system
DC01 (server)10.42.85.10Windows Server 2012 R2 Standard
DESKTOP-SDN1RPT10.42.85.115Windows 10 Enterprise Evaluation

I identified the server’s OS from license.rtf under Windows\System32\Licenses in FTK Imager, and the desktop’s from the SOFTWARE hive (Microsoft\Windows NT\CurrentVersion) in Registry Explorer.

The evidence arrived as one archive, Project Images.7z, with published MD5 and SHA1 values. Inside were eleven more archives, each with its own MD5:

SourceEvidence
NetworkPacket capture (PCAP)
DC01Disk image (E01), memory dump, pagefile, protected files, Autoruns output
DESKTOP-SDN1RPTDisk image (E01), memory dump, pagefile, protected files, Autoruns output

Before any analysis, I hashed everything in PowerShell and compared the results with the supplied values. Every hash matched, so the files I examined were the files that were collected.

I could not get Magnet AXIOM running, so I built the investigation on free tools: FTK Imager and Autopsy for the disk images, Wireshark for the network capture, and Eric Zimmerman’s Registry Explorer, EvtxECmd, MFTECmd and Timeline Explorer for registry, event log and file system artifacts.

A one-hour gap between sources

The first thing to sort out was time. The server’s SYSTEM hive (ControlSet001\Control\TimeZoneInformation) shows it set to Pacific Standard Time. Yet the host artifacts and the PCAP disagreed by exactly one hour. The malware’s $MFT creation time, for example, sat one hour after the moment the PCAP shows it being downloaded.

The cause is a misconfigured host, as the case author explains. The victim is in Colorado, on Mountain time (UTC−6 in September), but the hosts were set to Pacific time (UTC−7) while their clocks showed the correct local time. Every timestamp recorded on the hosts is therefore one hour later than reality, while the network capture is correct.

In practice, searching the host logs at the times seen in the PCAP turns up nothing. All times in this article are UTC, aligned to the PCAP, with host times shifted back one hour.

Preparing the artifacts

Raw disk images are hard to read directly, so I pulled out the artifacts that record activity and converted them into searchable timelines:

  • File system activity. In Autopsy, I exported the NTFS change journal ($Extend\$UsnJrnl:$J) and the $MFT from each image, then parsed them with MFTECmd into CSV files for Timeline Explorer. The journal shows when files were created, renamed, modified and deleted.
  • Registry. From Windows\System32\config in FTK Imager, I exported the SYSTEM and SOFTWARE hives and opened them in Registry Explorer for OS, network and service configuration.
  • Event logs. From Windows\System32\winevt\Logs, I exported each host’s Security.evtx, converted it to CSV with EvtxECmd, and loaded it into Timeline Explorer.
  • Network. The PCAP went into Wireshark to follow RDP sessions, HTTP downloads and internal connections.

How the attacker got in

The way in was an RDP brute force against the domain controller, and the PCAP shows it plainly.

At 02:19, 194.61.24.102 scanned TCP port 3389 (RDP) on DC01 with Nmap. At 02:21 it began brute-forcing the RDP login, and within the same minute it logged in successfully as Administrator. A domain controller with RDP reachable from the internet had its administrator password guessed.

The malware: coreupdater.exe

Once inside, the attacker installed a Metasploit payload named coreupdater.exe on the server, and later on the desktop, and made it persistent as a Windows service.

Delivery and identification

At 02:24:06, Internet Explorer inside the attacker’s RDP session downloaded coreupdater.exe over HTTP from 194.61.24.102, the same address behind the brute force. The PCAP shows the same file sent to the desktop later.

Wireshark can rebuild files from HTTP traffic (File → Export Objects → HTTP), so I exported the executable and hashed it. The same hash also appears in the Autoruns output. VirusTotal flags it as malicious, lists its behaviour as mostly dropping files and network communication, and ties it to Metasploit. In other words, it is free and easy to obtain.

VirusTotal also places 194.61.24.102 in Russia. That describes the address, not necessarily the person using it.

Where it lives and how it got there

Timeline Explorer places the file at C:\Windows\System32\coreupdater.exe, which I confirmed in both FTK Imager and Autopsy. Its $MFT creation time matches the download in the PCAP once the one-hour offset is removed.

A file downloaded through a browser lands in the user’s Downloads folder by default, not in System32. The change journal explains the difference: it records the file being deleted and created at the same instant, the typical trace of a move. The attacker moved the payload into a system folder where it would look routine.

Persistence

The change journal shows the payload moved and executed at 02:24:12 on DC01 and at 02:40:00 on the desktop. In the SYSTEM hive, Registry Explorer shows it registered as a Windows service, installed at 02:27:49 to start automatically with LocalSystem privileges. Both machines carry the same file in System32.

Calling home

VirusTotal links the hash to 56 IP addresses. Only one, 203.78.103.109, had any detections (7 of 94 engines). That same address appears in the PCAP right after coreupdater.exe started on DC01, which makes it the most likely command-and-control server.

Moving to the desktop

At about 02:35, the attacker used the server as a stepping stone to reach the desktop over RDP.

The PCAP shows an RDP connection from DC01 (10.42.85.10) to the desktop (10.42.85.115). The desktop’s Security log records a matching successful logon (event 4624) coming from DC01. The same pair of addresses gives the network layout: two hosts in 10.42.85.0/24, which Autopsy confirms under ControlSet001\Services\Tcpip\Parameters\Interfaces in each machine’s SYSTEM hive.

On the desktop, the attacker repeated the playbook. At 02:40, Internet Explorer downloaded coreupdater.exe from 194.61.24.102 again, and around 02:41 it was installed the same way as on the server.

What was taken

The attacker collected the contents of the server’s Secret share, including the Szechuan sauce recipe, zipped them and sent them out, then did the same on the desktop.

On the server, the change journal shows every file under FileShare\Secret being opened and closed during the breach. Around 02:30, an archive named secret.zip, matching the folder’s name, was created. Around 02:31 it was sent out over the Meterpreter session and deleted. Szechuan Sauce.txt shows access at 02:32:21.

Because the archive was deleted, I cannot list exactly what it contained. But every file in the share was opened, an archive named after the folder appeared and vanished within minutes, and the recipe later surfaced on the dark web. I concluded the recipe was stolen in this window, roughly 02:30 to 02:33.

On the desktop, the same thing happened with a different name: loot.zip was created around 02:46, then sent out and deleted around 02:48.

Who had logged on

The protected-files extracts show which accounts had logged on to each machine. On DC01, only Administrator. On the desktop, Admin, Administrator, mortysmith and ricksanchez.

Covering tracks

The attacker also tampered with the share: one file was swapped for a fake, and the fake was given false timestamps.

A swapped secret

At 02:34, SECRET_beth.txt was deleted from the Secret share and a new file, Beth_Secret.txt, appeared with different content. The original was not gone. Autopsy’s Recycle Bin artifact lists a recycled file, $RU2L112.txt, whose metadata still records its original name, SECRET_beth.txt. Its content: “Earth beth is the real beth.”

A timestomped file

Around 02:38, the timestamps of Beth_Secret.txt were changed to match PortalGunsPlans.txt in the same folder, so a directory listing makes the fake look as old as the real files. Two artifacts gave it away. Timeline Explorer shows a BasicInfoChange as the file’s last journal entry, and in the $MFT its last-modified and last-record-change times no longer line up the way they should.

Timestomping rewrites some timestamps, but the record of the rewrite stays behind.

Recommendations

This breach needed no exotic exploit: a domain controller with RDP open to the internet and a guessable administrator password were enough. My remediation report split the response into immediate actions and longer-term prevention.

Immediate remediation

  1. Isolate DC01 and the desktop from the network to stop further movement.
  2. Delete coreupdater.exe from System32 on both machines and stop its processes.
  3. Reset all passwords, starting with Administrator, and add multifactor authentication to critical accounts.
  4. Restore SECRET_beth.txt from the Recycle Bin and correct the timestomped file’s timestamps.
  5. Document every step and notify stakeholders and authorities as compliance requires.

Preventing a repeat

  • Restrict RDP. Disable external access, or put it behind a VPN and strict firewall rules, and require Network Level Authentication.
  • Protect endpoints. Run real-time anti-malware and an endpoint detection and response (EDR) tool.
  • Segment and monitor the network. Limit lateral movement between systems and watch traffic for anomalies.
  • Fix the processes. Keep an incident response plan and drill it, train staff, enforce patch management, and apply least privilege with regular account audits and credential rotation.
  • Think long term. Move toward a Zero Trust model, and align with CIS Control 12 (Network Infrastructure Management), CIS Control 13 (Network Monitoring and Defense) and SANS guidance on secure network device configuration.

Conclusion

There was a breach, and the evidence traces it end to end: an RDP brute force against the domain controller, a Metasploit payload made persistent as a service, the Secret share zipped and sent out, a pivot to the desktop to do it again, and a swapped, timestomped file left behind.

No single source told the whole story. The PCAP showed the way in and the command-and-control traffic. The event logs tied sessions to machines. The change journal and $MFT exposed the payload’s move, the staging archives and the timestomp, and the registry explained the persistence and the time zone. Lining them up, after first making sure they agreed on the time, is what turned a pile of artifacts into a timeline.

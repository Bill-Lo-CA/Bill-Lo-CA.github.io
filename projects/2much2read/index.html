2Much2Read: A Local-LLM Newsletter Digest

A local-first pipeline that reads selected Gmail newsletters, extracts and ranks their stories with three local models, folds duplicate coverage together, and posts one daily digest to a private Discord channel. This page covers how a run works, the measurements behind the main design decisions, and the security boundaries around it.

By Bill Lo · November 10, 2026 · Source on GitHub

Technology and security newsletters overlap heavily. The same model release or CVE arrives from several senders on the same morning, each issue mixes in sponsored entries, and links arrive wrapped in click trackers that identify the subscriber. The few stories worth reading are buried under the rest.

2Much2Read reads only the newsletters configured for it, does all of its language-model work on the local machine by default, and sends nothing but the finished digest to Discord. It runs every morning on a systemd timer. The same repository holds three companion tools that share its runtime helpers, described at the end of this page.

At a glance

How a run works

Gmail / Hacker News→Extract→Rerank→Review→Merge & Rewrite→Discord
  1. Prepare each email. Every URL in the text is replaced by a short candidate code such as [L7], and unsubscribe or non-candidate links are removed. The extractor never needs a URL, and they were most of the tokens: this cut one issue of The New Stack from 21,354 tokens to 2,707.
  2. Extract stories. The small model first lists the issue’s stories and marks the sponsored ones, then writes an item for each. Counting first instead of capping at ten raised coverage over 12 TLDR issues from 91 of 165 stories to 147.
  3. Translate and check titles. A translation model brings titles into the digest language. Each title is then read back into English without the original in view and compared with the newsletter’s own headline, which catches mistranslations such as “distillation” coming back as “diffusion”.
  4. Rerank. The reranker scores up to 100 candidates. Seven of the twenty reviewer slots are reserved for security stories, because on a single scale AI releases outrank vulnerability disclosures: in one run only 3 of 23 security items reached the global top 20.
  5. Review. The review model picks the headlines. If none of them is a security story and no CVE is among the mentions, the best security story takes the last headline slot.
  6. Merge and rewrite. Coverage of the same story from several newsletters is folded into one entry, stories that repeat from the previous three days are marked, and each headline is rewritten from its full article rather than the few lines the extractor saw.
  7. Deliver. The digest goes to Discord. Each confirmed chunk is checkpointed, so a retry sends only what has not arrived.

Three models on one 8 GB GPU

The extractor, reranker and reviewer never share memory. The extractor and translator are released before the reranker loads, and the reranker is released before the reviewer starts. The reranker runs on the CPU unless the GPU has room to spare. Even alone, qwen3:8b at a 16,384-token context needs roughly 8 GB for its weights plus the KV cache, so the project documents running Ollama with a quantized KV cache and checking the real footprint with ollama ps rather than trusting the setting.

Context limits turned out to be a correctness and security issue, not only a performance one. Ollama truncates an oversized prompt from the head without raising an error, which silently drops the system prompt while keeping the untrusted newsletter text. Every prompt is therefore bounded against the context window before it is sent: candidates and newsletter text are trimmed from the tail, and the prompt-injection guard is repeated after the untrusted block.

Decision: asking the model instead of counting words

Deciding whether two entries describe the same story was first done by token overlap. Six successive review rounds each found a new class of pair it got wrong: common lowercase words, bare acronyms, Title Case headlines, and titles the extractor never translated. Over 476 real items, 17 unrelated pairs still merged, such as two different stories that both named Claude Code. The question is semantic and the method was lexical, so each fix only exposed the next case.

Token overlap now only decides which pairs are worth asking about. A pair that shares a distinctive token is shortlisted, and the review model answers one yes-or-no question for it. A loose shortlist costs a generation rather than a wrong digest. On real runs it shortlists 0 to 15 pairs per digest, typically 2 to 5, and a budget caps a pathological run. When the budget runs out or the model fails, the answer is no, because a missed merge only loses an attribution while a wrong merge gives one headline another story’s article.

A yes-or-no answer was chosen over a 0–100 score after measuring both:

MeasurementResult (0–100 score unless noted)
Distinct pairs0, 0, 0, 0, 0, 0, 20, 30
True duplicates50, 85, 95, 95, 100, 100
Threshold gap20 points
Order swappedMoved a score by up to 35 points; never flipped the yes-or-no answer
Yes/no accuracy9 of 10 known pairs; the one miss declined to merge, the safe direction

The gap a threshold would sit in was narrower than the noise from presentation order alone, so whether two entries merged would have depended on which one happened to be the headline. A discrete judgement is what makes the answer stable.

Keeping the digest honest

A small model summarizing a newsletter will happily produce a confident sentence from a bare title. Several checks keep that out of the headlines:

  • A headline needs a source. Only items with an article to read, coverage from another newsletter, or a full text the extractor read can become headlines. On one day two of the first six headlines had been one-line guesses from a link list, and one of them was wrong.
  • Repeats must add facts. For a story seen in the previous days, the review model lists today’s concrete facts and keeps only those no earlier report stated. Asked for a verdict alone, it called all 19 repeated headlines from 15 to 22 October new; made to list and check, it found 9 with nothing new, each a genuine repeat.
  • Titles are checked against the source. Over 468 re-extracted titles the back-translation check flagged 39, about nine of which had changed facts, such as $3.8m becoming $38,000.
  • Rewrites fail closed. A headline rewrite is discarded when the fetch or model fails, when the model says the source is about something else, or when it answers in the wrong language, and it is never attempted when trimming would leave no source text.
  • Script is corrected by clause. Traditional Chinese output that slips into Simplified is converted with zhconv-rs only in clauses that contain a Simplified-only character. Over 1,923 stored items this changed 46 fields and nothing else.

Security boundaries

The pipeline reads untrusted email, follows links chosen by third parties, and holds OAuth tokens and a Discord credential, so most of its boundaries are explicit:

  • Link following. Every redirect hop is validated like the first request: public addresses only, ports 80 and 443, no credentials, at most five hops. A script-based click page is parsed for its next hop, never executed. Downloads other than pages and PDFs are refused, so a digest never links an executable or archive.
  • Subscriber privacy. Shown links drop campaign tags and the parameters that identify the recipient, such as HubSpot’s _hsenc and Mailchimp’s mc_eid. A link that is still a tracker after cleaning is not shown at all. Email bodies are never stored, only their hash and length.
  • Local models by default. Ollama is reached locally and ignores proxy variables. A remote server requires an explicit opt-in and HTTPS, because email content would then leave the machine.
  • Credentials. Discord webhooks must be HTTPS URLs on official Discord hosts with the standard path. OAuth tokens and the bot token live only in 0600 files outside the repository. Library loggers stay at WARNING because httpx logs full request URLs at INFO, and a webhook URL carries its token.
  • Service sandboxing. Each systemd unit is sandboxed, and every exemption is documented with its reason. The GPU unit alone keeps device access; it also allows the scheduling calls PyTorch makes when the reranker loads, after a denied call killed one run with SIGSYS nine minutes in. The two long-running companion services answer only over Tailscale, and their home directory holds only the code and the few files they need.

Failure handling

A scheduled job has no one watching it, so failures are designed to be resumable and specific. Discord delivery is checkpointed per chunk and destination. A run that cannot finish ends on one line naming the error and its remedy, such as AUTH_REAUTH_REQUIRED or LOCK_CONTENDED, rather than a traceback.

Model timeouts get the same care. If extracting one email times out, the run ends without marking that email failed, because a stalled Ollama would otherwise fail every email. The next run gives it two tries and sends a one-token probe: if the model still answers, that one email is marked failed and the run continues; if it does not, Ollama is the problem and the email is kept for later.

Testing and CI

Every pull request and push to main runs ruff formatting and lint checks, strict mypy, more than 1,100 tests and a package build. The tests also run on Python 3.11 and 3.13, the edges of the supported range, after 3.13 changed how symlink loops resolve and broke an assumption in a permissions test.

Line coverage cannot show whether a test would notice a wrong comparison or a missing check, so a weekly workflow runs mutation testing with mutmut over the modules that guard a security boundary: endpoint and webhook validation, Discord delivery and mention control, file permissions, OAuth tokens, the article fetcher’s network policy, and the two network-facing services. The workflow fails when any of those modules has code no test reaches. mutmut never changes validators, CLI commands, regexes or constants, so a clean report says nothing about them and they need tests of their own.

Companion tools

The repository grew into four commands with separate configuration, databases and OAuth clients. They share only small runtime helpers such as path resolution, Discord delivery and a process lock.

Conclusion

Most of the work in 2Much2Read is not in calling a model but in deciding what the model is allowed to decide, measuring it, and failing safely when it is wrong. The duplicate judgement and the repeat check followed the same pattern: try the simplest approach, measure where it breaks on real data, and replace it with a narrower question the model answers reliably.

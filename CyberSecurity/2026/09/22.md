# 2026-09-22｜每日資安學習

## 1/4｜每日資安小知識：Kerberos 票證、PAC 與 Windows Access Token 到底怎麼串起來？

今天的重點不是「Kerberos 怎麼登入」，而是把 **authentication（驗證）** 與 **authorization（授權）** 接起來：一個使用者拿到 Kerberos 票證之後，Windows 最後到底根據什麼決定「這個 process 能不能讀檔、開服務、碰 registry、存取遠端 share」？

核心 mental model 是：

**Kerberos ticket 證明你是誰／帶著哪些宣告 → Windows 登入流程把這些資訊轉成 access token → 每次存取 securable object 時，Security Reference Monitor 依 token 與 Access Control List 做授權判斷。**

這也是為什麼 Golden Ticket、Diamond Ticket、SIDHistory、群組巢狀關係、委派與本機管理員權限最後都會在「Access Token 裡有什麼」這一層交會。

### 1. 核心概念與它解決的問題

在 Microsoft Active Directory 環境裡，Kerberos 解決的是網路身分驗證與服務票證問題，但 Windows 本機與伺服器上的授權判斷不能每次都回 Domain Controller 查一次。

因此 Windows 需要一個可以在本機快速使用的授權資料結構：**Access Token（存取權杖）**。

Access Token 會附著在 process / thread 的安全內容上，常見內容包括：

- 使用者的 SID (Security Identifier，安全性識別碼)
- 群組 SID
- 特權，例如 SeDebugPrivilege、SeBackupPrivilege
- Integrity Level（完整性層級）
- Logon SID
- Restricted SID
- Token type、impersonation level
- 某些 UAC (User Account Control，使用者帳戶控制) 情境下的 linked token

當程式嘗試開啟檔案、registry key、service、named pipe、process 等 securable object 時，Windows 會把 token 與物件的 security descriptor 比對，決定允許或拒絕。

所以「我拿到票了」不等於「我一定有權限」；票證中的 identity / group information 最後必須能形成一個具有足夠 SID 與 privilege 的 token。

### 2. 底層流程：從 KDC 到 PAC，再到 Access Token

先拆成幾層。

#### Kerberos 層

KDC (Key Distribution Center，金鑰發配中心) 通常存在於 Domain Controller 上，主要提供兩類功能：

- AS (Authentication Service，驗證服務)：核發 TGT (Ticket Granting Ticket，票證授予票證)
- TGS (Ticket Granting Service，票證授予服務)：根據 TGT 核發給特定 service 的 service ticket

使用者登入後，取得 TGT；之後要連 CIFS (Common Internet File System)、HTTP、MSSQLSvc、HOST 等服務時，再向 TGS 要對應 service ticket。

#### PAC 層

Windows Kerberos ticket 通常包含 PAC (Privilege Attribute Certificate，權限屬性憑證)。

PAC 可以把它理解成「由網域端提供給服務端的授權資料包」，裡面可包含：

- user SID
- group memberships
- domain group information
- logon information
- extra SID
- user flags
- claims 等

它的重要價值是：服務收到 ticket 後，不必每次為了知道使用者屬於哪些群組，都同步查詢 Domain Controller。

這是一個重要的效能與可用性 trade-off：**把授權資訊塞進已簽章的 ticket，可以減少即時查詢，但也會讓授權資訊在票證生命週期內具有一定程度的「快取」性。**

例如你剛把某人從高權限群組移除，他現有的票證或登入 session 不一定立刻完全反映新的權限狀態；常見處理方式是重新登入、purge Kerberos tickets，或等待票證生命週期。

#### LSA / LSASS 層

LSA (Local Security Authority，本機安全性授權機構) 與 LSASS (Local Security Authority Subsystem Service，本機安全性授權子系統服務) 負責 Windows 很多安全性工作，包括登入 session、authentication package、security policy 與 token 建立流程。

當網路或互動式登入成功，Windows 會建立 logon session，並依登入取得的 identity、group membership、local policy 等建立 Access Token。

此時 Kerberos ticket 不是「直接拿去讀 NTFS 檔案」；Windows 會把身分驗證結果轉換成本機授權可以理解的 token。

### 3. Access check：Windows 真正怎麼決定你能不能碰一個物件

Windows securable object 通常有 security descriptor，其中包含：

- Owner
- DACL (Discretionary Access Control List，自主存取控制清單)
- SACL (System Access Control List，系統存取控制清單)

DACL 裡由多個 ACE (Access Control Entry，存取控制項目) 組成，例如：

- Allow Domain Admins: Full Control
- Allow Helpdesk: Read
- Deny SomeGroup: Write

當 process 呼叫 API 開啟物件時，Windows Security Reference Monitor 會進行 access check，概念上會拿：

**Access Token 裡的 SID / privilege + 物件 DACL + requested access mask**

來判斷結果。

這裡有幾個重要觀念：

1. **Group membership 不是抽象概念，而是最後會以 SID 形式影響 access check。**
2. **Privilege 與 ACL permission 是不同路徑。**  
   例如 SeBackupPrivilege 可能允許 backup software 在特定 API / flag 下繞過一般檔案 DACL，而不是因為使用者突然被加入檔案 ACL。
3. **Impersonation 可以讓 thread 暫時用另一個 token 做 access check。**  
   這也是 Windows service、RPC (Remote Procedure Call，遠端程序呼叫)、SMB (Server Message Block，伺服器訊息區塊) 等許多 delegation / impersonation 行為的基礎。

### 4. SIDHistory 為什麼敏感

SIDHistory 是為了 Active Directory migration 設計。

例如：

- 舊網域使用者 SID：S-1-5-21-OLD-1001
- 新網域使用者 SID：S-1-5-21-NEW-2001

企業搬網域時，如果所有 file server ACL 都還寫著舊 SID，直接改 SID 會造成大量權限失效。

所以新帳號可以暫時保留舊 SID 到 SIDHistory，讓 access check 仍然能匹配舊 ACL。

設計目的非常合理：降低 domain migration 成本。

攻擊面也很明顯：如果攻擊者能不當寫入高權限 SID 到 SIDHistory，最後建立的 token 可能攜帶那個額外 SID，授權判斷就可能把它當成高權限主體。

因此 SIDHistory 的風險不是「Kerberos 被破解」，而是：

**authorization data 被污染 → PAC / directory identity data 帶入登入流程 → token 帶著額外 SID → access check 得出攻擊者想要的結果。**

### 5. PAC 與 Golden / Diamond Ticket 的連結

你已經熟 Golden Ticket，所以這裡直接講差異。

Golden Ticket 的關鍵是使用 KRBTGT 帳號的長期金鑰，偽造一張新的 TGT，攻擊者可以控制很多 ticket 內容，包括 PAC 中的身分與群組資訊。

Diamond Ticket 的思路比較隱蔽：先取得一張合法 TGT，再修改其中 PAC 等資料並重新處理相關加密／簽章，使票證在很多欄位上更像真實 KDC 流程產生的 ticket。

真正值得建立的 mental model 不是「哪一種 ticket 比較強」，而是：

**攻擊者最終想控制的是 authorization context。Kerberos ticket / PAC 是把這個 context 從 Domain Controller 帶到 service 的載體，而 Access Token 是 Windows 真正執行授權時使用的本機表示。**

### 6. 具體攻防情境

假設攻擊者已取得一個 domain user，之後透過錯誤委派或 Active Directory 權限取得能影響某高權限帳戶 authorization data 的能力。

攻擊鏈可能不是直接「加進 Domain Admins」。

更隱蔽的作法可能是：

1. 攻擊者取得合法 Kerberos logon material。
2. 票證中的 PAC 出現異常 group SID / extra SID。
3. 目標伺服器接受票證。
4. Windows 建立包含高權限 SID 的 token。
5. 該 token 對檔案、service control manager、remote registry 或 admin share 進行成功的 access check。
6. SOC 看到的是「一個看似正常帳號成功登入」，但實際 authorization context 超出帳號平常應有權限。

Blue Team 如果只盯「登入失敗次數」就很容易錯過，因為這種攻擊常常是 **valid authentication + abnormal authorization**。

### 7. Detection / Investigation：應該看什麼

#### Windows Security Log

常見有價值的 Event ID：

- **4624**：Successful logon。看 logon type、source address、authentication package、account。
- **4672**：Special privileges assigned to new logon。高權限登入常見，但需與帳號基線比對。
- **4768**：Kerberos Authentication Service ticket requested，也就是 TGT request。
- **4769**：Kerberos service ticket requested。
- **4627**：Group membership information，部分情境可協助理解登入 token 對應的群組。

單看一筆事件通常不夠，重點是 correlation。

例如：

- 一個平常不是 admin 的帳號突然在多台 server 產生 4672。
- 4769 顯示該帳號突然大量請求 CIFS / HOST / LDAP service tickets。
- 4624 後緊接著 Service Control Manager、scheduled task、remote service 等橫向行為。
- 帳號的 directory group membership 與實際登入後呈現的授權行為不一致。

#### Active Directory telemetry

要看：

- 高權限群組 membership 變更
- SIDHistory 寫入或異常值
- directory object ACL 修改
- delegation 設定變更
- 帳號屬性被異常修改
- KRBTGT reset / key lifecycle 與異常 Kerberos 活動

#### EDR

EDR (Endpoint Detection and Response，端點偵測與回應) 能補上「登入之後做了什麼」。

例如：

- 非預期 process 获得 elevated token
- token duplication / impersonation 行為
- 對 LSASS 的可疑 handle access
- 服務建立
- remote execution chain
- unusual parent-child process
- admin share / named pipe 使用

這裡的核心是：**Authentication log 告訴你誰進來；EDR 行為告訴你拿到的權限被怎麼使用。**

### 8. False Positive 與限制

高權限 token 不一定就是攻擊。

常見合法來源包括：

- backup agent
- endpoint management
- vulnerability scanner
- software deployment
- service account
- administrator jump host
- scheduled maintenance
- domain management tool

所以偵測不能只寫：

「看到 4672 → alert」

更好的思路是建立 context：

- 這個帳號平常會不會在這台 host 上登入？
- source host 是否合理？
- logon type 是否符合預期？
- 後續是否出現 service creation、remote registry、PowerShell、WMI (Windows Management Instrumentation，Windows 管理規範) 等行為？
- 使用者是否真的在對應高權限群組？
- 同時間是否有 directory change？

另外，ticket / PAC 的某些細節不一定完整呈現在標準 Windows Event Log；成熟的偵測往往需要 Domain Controller log、endpoint telemetry、network authentication telemetry 與 Active Directory change auditing 一起看。

### 9. 設計上的 Trade-off

為什麼不乾脆每次 access check 都回 Domain Controller 查最新群組？

因為這會帶來：

- 巨大延遲
- Domain Controller 負載
- 網路相依性
- Domain Controller 短暫不可用時，全網授權可能跟著失效

因此系統選擇讓 identity / authorization context 具有一定的 ticket 與 session 狀態。

代價就是：

- 權限撤銷不是永遠立即生效
- stolen ticket 在有效期間可能繼續可用
- authorization data 本身變成高價值攻擊面
- 偵測需要理解 ticket、directory 與 endpoint token 三個層次

這跟 JWT (JSON Web Token) 的設計 trade-off 很像：token 驗證可以很快、很分散，但 revocation 與 stale claims 就變得麻煩。

### 10. 與其他概念的連結

#### 與 JWT 的對比

JWT 常把 claims 放進簽章 token；Kerberos PAC 也在 ticket 中攜帶 authorization-related data。

共同問題是：

**被簽章的 claims 不代表 claims 永遠是最新狀態。**

因此 stateless / semi-stateless authorization 的效能優勢，通常會換來 revocation、freshness 與 monitoring 的複雜度。

#### 與 Linux credentials 的對比

Linux process 也有 UID (User Identifier，使用者識別碼)、GID (Group Identifier，群組識別碼)、supplementary groups、capabilities 等 credentials。

概念上與 Windows Access Token 很接近：

**process 帶著 security context → kernel 對 object / syscall 做權限判斷。**

差別在 Windows token 結構、SID、privilege、integrity level、impersonation 等機制更豐富。

#### 與 Zero Trust 的連結

Zero Trust 不只是「每次登入都 MFA (Multi-Factor Authentication，多因素驗證)」。

真正成熟的 Zero Trust 會關心：

- authentication 強度
- device posture
- session context
- authorization scope
- privilege lifetime
- continuous evaluation

也就是不要把「成功登入」誤認成「接下來所有操作都值得信任」。

### 今天應該記住

1. **Kerberos ticket 負責攜帶驗證與授權資訊，但 Windows 真正做本機 access check 時依靠的是 Access Token。**
2. **PAC 是 Kerberos 與 Windows authorization 之間的重要橋樑；攻擊 PAC 的價值在於操控最後形成的授權 context。**
3. **SIDHistory 本來是 migration 相容性功能，但若被濫用，額外 SID 可以直接影響 access check。**
4. **偵測高階 Kerberos / identity 攻擊不能只看 authentication failure，要關聯 TGT / service ticket、group / directory change 與 endpoint post-logon behavior。**
5. **把授權資料放進 ticket / session 是效能與可用性的設計選擇，代價是 revocation、stale privilege 與 detection complexity。**

## 2/4｜CySA：事件回應中的證據蒐集

### English original

An incident response team found IoCs in a critical server. The team needs to isolate and collect technical evidence for further investigation. Which of the following pieces of data should be collected first in order to preserve sensitive information before isolating the server?

A. Hard disk  
B. Primary boot partition  
C. Malicious files  
D. Routing table  
E. Static IP address

### 中文完整翻譯

事件回應團隊在一台關鍵伺服器中發現了 IoCs (Indicators of Compromise，入侵指標)。團隊需要隔離該伺服器，並蒐集技術證據以進一步調查。為了在隔離伺服器之前保留重要資訊，下列哪一項資料應該最先蒐集？

A. 硬碟  
B. 主要開機分割區  
C. 惡意檔案  
D. 路由表  
E. 靜態 IP 位址

---

### 答案與解析

**正確答案：D. Routing table**

#### 為什麼正確

這題考的是 **order of volatility（揮發性順序）**。

Routing table（路由表）主要存在於系統目前的 runtime state 中。當主機關機、重開機、網路介面重置，或被隔離後，路由資訊可能改變或消失。

因此在進行可能破壞 runtime state 的動作前，應優先蒐集：

- active network connections
- routing table
- ARP (Address Resolution Protocol，位址解析協定) cache
- running processes
- logged-on sessions
- memory-resident information

這些資訊通常比磁碟內容更容易因操作而消失。

#### 其他選項為什麼不對

**A. Hard disk**  
硬碟屬於相對持久的 non-volatile evidence。即使主機被隔離，磁碟資料通常仍然存在，可以之後做 forensic image。

**B. Primary boot partition**  
同樣是持久性儲存的一部分，不會因為先拔網路或做基本隔離就立刻消失。

**C. Malicious files**  
惡意檔案如果已經寫入磁碟，通常比 network / memory state 更不易消失。它很重要，但不是這些選項裡最 volatile 的。

**E. Static IP address**  
靜態 IP 通常來自持久性網路設定；就算斷網，多數情況仍能從系統設定、configuration files 或 registry 重建。

#### 背後要掌握的 CySA / 實務概念

DFIR (Digital Forensics and Incident Response，數位鑑識與事件回應) 中最經典的原則之一就是先保存最容易消失的證據。

大致可以想成：

CPU / registers / cache → RAM → network state / process state → temporary files → disk → remote logs / backups

實際順序會依 incident 與環境調整，但原則不變：**先抓一旦隔離、關機或重啟就可能消失的東西。**

#### SOC / IR 記憶點

**不要把「隔離主機」當成完全沒有鑑識副作用的按鈕。**

隔離前至少要思考：我現在會不會因此失去 active connection、route、ARP cache、memory-only malware、process tree 或 session 資訊？

## 3/4｜CySA：SOC 工作自動化判斷

### English original

Which of the following security operations tasks are ideal for automation?

A. Suspicious file analysis:  
Look for suspicious-looking graphics in a folder.  
Create subfolders in the original folder based on category of graphics found.  
Move the suspicious graphics to the appropriate subfolder

B. Firewall IoC block actions:  
Examine the firewall logs for IoCs from the most recently published zero-day exploit  
Take mitigating actions in the firewall to block the behavior found in the logs  
Follow up on any false positives that were caused by the block rules

C. Security application user errors:  
Search the error logs for signs of users having trouble with the security application  
Look up the user's phone number  
Call the user to help with any questions about using the application

D. Email header analysis:  
Check the email header for a phishing confidence metric greater than or equal to five  
Add the domain of sender to the block list  
Move the email to quarantine

### 中文完整翻譯

下列哪一項安全營運工作最適合自動化？

A. 可疑檔案分析：  
在資料夾中尋找看起來可疑的圖片。  
依找到的圖片類別，在原始資料夾中建立子資料夾。  
把可疑圖片移動到適當的子資料夾。

B. 防火牆 IoC 封鎖操作：  
檢查防火牆日誌，尋找最近公布的 zero-day 漏洞相關 IoC。  
在防火牆上採取緩解措施，封鎖日誌中發現的行為。  
追蹤封鎖規則造成的 false positive（誤報）。

C. 安全應用程式使用者錯誤：  
搜尋 error log，找出使用者操作安全應用程式時遇到問題的跡象。  
查詢使用者的電話號碼。  
打電話協助使用者處理使用問題。

D. 電子郵件標頭分析：  
檢查 email header，確認 phishing confidence metric 是否大於或等於 5。  
把寄件者的 domain 加入 block list。  
將郵件移至 quarantine。

---

### 答案與解析

**正確答案：D. Email header analysis**

#### 為什麼正確

自動化最適合的工作通常具備：

- input 結構化
- 判斷條件清楚
- 流程固定
- output / action 可以明確定義
- 人工判斷需求低

D 幾乎就是一個 deterministic workflow：

1. 讀取 phishing score。
2. 判斷 score >= 5。
3. 將 domain 加入 block list。
4. quarantine 郵件。

這種流程很適合由 SOAR (Security Orchestration, Automation, and Response，安全協調、自動化與回應) 或 mail security platform 執行。

#### 其他選項為什麼不對

**A. Suspicious file analysis**  
「suspicious-looking graphics」本身就是高度主觀的判斷。若沒有明確 classifier、hash、metadata 或 detection rule，單靠「看起來可疑」不適合直接自動化。

**B. Firewall IoC block actions**  
其中部分步驟可以自動化，例如 ingest IoC、比對 logs、建立暫時性 block；但題目把「最新 zero-day 的 mitigating action」與 false positive follow-up 也一起包進流程，需要較多 context 與人工風險判斷。直接自動改 firewall policy 的 blast radius 也比較高。

**C. Security application user errors**  
log 搜尋與聯絡資訊查詢可以自動化，但「打電話理解使用者問題」本質上需要人類互動。

#### 背後要掌握的 CySA / 實務概念

好的 SOC automation 不等於「能寫 script 就全部自動」。

可以用兩個維度判斷：

**Decision ambiguity：** 判斷是不是清楚？  
**Action blast radius：** 做錯會造成多大影響？

最適合 full automation 的通常是：

- low ambiguity
- low / bounded blast radius
- high repetition
- machine-readable inputs

高 blast radius 動作則常適合 human-in-the-loop，例如先自動 enrich、產生建議，再由 analyst approve containment。

#### 題庫答案的實務校正

D 是題庫與考試邏輯下的最佳答案，但真正 production 環境裡，「自動封鎖整個 sender domain」仍要考慮信譽良好的 shared domain、compromised legitimate domain 與供應商信件。

成熟做法常會依 confidence score、domain reputation、DMARC (Domain-based Message Authentication, Reporting, and Conformance，網域型郵件驗證、報告與一致性)、SPF (Sender Policy Framework，寄件者政策框架)、DKIM (DomainKeys Identified Mail，網域金鑰識別郵件)、URL / attachment verdict 等資料做多條件判斷，而不是單一 score 無條件永久封鎖。

#### SOC / IR 記憶點

**Automation 的最佳目標不是「最複雜的工作」，而是「規則清楚、重複度高、資料結構化，而且錯誤影響可控制的工作」。**

## 4/4｜CySA：Wireshark 中的 FTP 資料流分析

### English original

A security analyst is reviewing a packet capture in Wireshark that contains an FTP session from a potentially compromised machine. The analyst sets the following display filter: ftp. The analyst can see there are several RETR requests with 226 Transfer complete responses, but the packet list pane is not showing the packets containing the file transfer itself. Which of the following can the analyst perform to see the entire contents of the downloaded files?

A. Change the display filter to ftp.active.port  
B. Change the display filter to tcp.port==20  
C. Change the display filter to ftp-data and follow the TCP streams  
D. Navigate to the File menu and select FTP from the Export objects option

### 中文完整翻譯

一名安全分析師正在 Wireshark 中檢查一份 packet capture（封包擷取），其中包含來自一台可能已遭入侵主機的 FTP (File Transfer Protocol，檔案傳輸協定) session。分析師設定了以下 display filter：

ftp

分析師可以看到數個 RETR request，以及對應的 226 Transfer complete response，但 packet list pane 中沒有顯示實際包含檔案傳輸內容的封包。下列哪一項操作可以讓分析師看到下載檔案的完整內容？

A. 將 display filter 改成 ftp.active.port  
B. 將 display filter 改成 tcp.port==20  
C. 將 display filter 改成 ftp-data，並追蹤 TCP (Transmission Control Protocol，傳輸控制協定) streams  
D. 前往 File menu，並在 Export objects 中選擇 FTP

---

### 答案與解析

**正確答案：C. Change the display filter to ftp-data and follow the TCP streams**

#### 為什麼正確

FTP 與 HTTP 最大的差異之一，是 FTP 傳統上把：

- control channel
- data channel

分開。

當 display filter 使用 **ftp** 時，Wireshark 主要顯示 FTP control protocol，例如：

- USER
- PASS
- RETR
- STOR
- PASV
- PORT
- 226 Transfer complete

真正的檔案 bytes 則走獨立的 data connection。

Wireshark 會把可辨識的 FTP data channel 解碼為 **ftp-data**。因此使用 ftp-data 找到資料連線，再 Follow TCP Stream，就可以重組該 TCP stream 的 payload，觀察被下載的內容。

#### 其他選項為什麼不對

**A. ftp.active.port**  
這不是用來直接顯示所有檔案 payload 的通用方式；而且 FTP 還可能使用 passive mode。

**B. tcp.port==20**  
FTP active mode 傳統上 server data connection 會使用 TCP port 20，但不能假設所有 FTP data 都固定出現在 port 20。

在 passive mode 中，server 會告訴 client 一個額外的高位 TCP port，資料通道走那個 negotiated port。因此只 filter tcp.port==20 很容易漏掉。

**C. ftp-data and follow the TCP streams**  
能直接定位資料通道並重組 stream，是最符合題意的作法。

**D. Export objects → FTP**  
題目的選項描述並不是 Wireshark 中最可靠、通用的 FTP reconstruction 路徑；此題標準思路是從 ftp-data stream 追蹤實際資料連線。

#### 背後要掌握的 CySA / 實務概念

FTP 的 control / data channel separation 對 network investigation 很重要。

典型 control flow：

1. client 連 TCP 21。
2. client 認證。
3. client 發送 RETR filename。
4. client/server 依 active 或 passive mode 建立另一條 data connection。
5. 檔案走 data channel。
6. control channel 回覆 226 Transfer complete。

所以看到 RETR 與 226，只能證明 control plane 表示一次 transfer 已完成；要取得實際內容，必須找到對應 data flow。

這個概念也提醒你：**只 filter application control protocol，可能會把真正重要的 payload 排除掉。**

#### SOC / IR 記憶點

在 packet analysis 裡，看到「控制命令」時要立刻問：

**真正的 data plane 是不是走另一條 connection、另一個 port、另一個 protocol，甚至另一台 host？**

FTP 是最經典的例子，類似 mental model 也可以延伸到 VoIP (Voice over Internet Protocol，網際網路語音)、RPC、某些 tunneling / control protocol 與 cloud control plane。

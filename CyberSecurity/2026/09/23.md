# 2026-09-23｜每日資安學習

## 1/4｜每日資安小知識：DNS 不只是「把網域轉成 IP」——從遞迴解析、快取到攻擊與偵測

DNS (Domain Name System，網域名稱系統) 表面上是名稱解析，但從資安角度，更重要的是理解「誰替誰查、答案可以被快取多久、哪一層能被欺騙，以及哪些 DNS 行為本身就是攻擊訊號」。

### 1. 核心概念與它解決的問題

典型 DNS 查詢鏈可以想成：

**stub resolver → recursive resolver → root → TLD → authoritative server**

Stub resolver 是 endpoint 上真正發起查詢的元件；recursive resolver（遞迴解析器）替 client 完成後續查詢並快取結果。Root 與 TLD (Top-Level Domain，頂級網域) 多半提供 referral；真正管理某個 zone 資料的是 authoritative server（權威名稱伺服器）。

這個設計解決了全球名稱空間的可擴展性：沒有任何一台 DNS server 需要知道所有名稱的最終答案。

### 2. Recursive 與 iterative 的差別

Client 常要求 recursive resolver：「請給我最後答案。」Resolver 往上游查詢時，則常使用 iterative query（迭代式查詢）。

例如查詢 `www.example.com`：

1. Client 問企業 recursive resolver。
2. 若 cache miss，resolver 問 root。
3. Root 告訴它 `.com` 的 name server。
4. Resolver 問 `.com` TLD server。
5. TLD 告訴它 `example.com` 的 authoritative server。
6. Resolver 問 authoritative server。
7. 最後得到 A / AAAA record，回給 client 並依 TTL 快取。

A record 對應 IPv4；AAAA record 對應 IPv6；CNAME (Canonical Name，標準名稱) 則會導向另一個 hostname，因此實際解析可能形成多段 chain。

### 3. Cache 與 TTL：效能與安全的共同邊界

TTL (Time To Live，存活時間) 決定 record 可以被 resolver 快取多久。

高 TTL 的好處：
- authoritative server 負載較低
- client latency 較低
- 短暫 DNS outage 時仍可能靠 cache 工作

代價：
- record 變更傳播較慢
- 錯誤或被污染的答案可能存活更久

低 TTL 則反過來：切換快，但 query volume 與上游負擔增加。

Negative answer 也可能被 cache。例如 NXDOMAIN 不是每次都重新一路問 authoritative server。

這對調查很重要：**authoritative DNS log 沒看到某 endpoint 的 query，不代表 endpoint 沒用過該 domain。它可能拿的是 recursive resolver cache。**

### 4. DNS transport：UDP、TCP、DoT、DoH

傳統 DNS 最常見使用 UDP (User Datagram Protocol，使用者資料報協定) port 53，因為 request/response 通常很小。

DNS 也會使用 TCP (Transmission Control Protocol，傳輸控制協定) port 53，例如：
- response 過大
- fallback
- zone transfer

現代環境還可能有：

- DoT (DNS over TLS，透過傳輸層安全性的 DNS)
- DoH (DNS over HTTPS，透過 HTTPS 的 DNS)

DoH 提高 client 到 resolver 的隱私與抗竄改能力，但對 SOC (Security Operations Center，安全營運中心) 來說會降低 network visibility。

因此「加密 DNS」不是純粹只有好處；它是在 **privacy 與 centralized visibility** 之間做 trade-off。企業通常要靠 endpoint policy、managed browser、approved resolver 與 EDR 補回可見性。

### 5. Cache poisoning 真正想騙的是什麼

DNS cache poisoning 的目的，是讓 resolver 暫時相信錯誤 mapping。

傳統 DNS 本身沒有對所有 answer 做 cryptographic authenticity 驗證。現代 resolver 會使用 transaction ID randomness、source-port randomization、bailiwick checking 等技術降低 spoofing 成功率。

DNSSEC (Domain Name System Security Extensions，網域名稱系統安全延伸) 則能對 DNS data 提供來源驗證與完整性。

但要記住：

**DNSSEC 不是加密。**

它解決的是「答案是不是由可信 zone 簽出、是否被竄改」；DoH/DoT 才是在保護 transport confidentiality/integrity。兩者不是同一層問題。

### 6. 攻防情境：DNS C2 與 tunneling

假設一台 workstation 每 60 秒查詢：

```text
k3m8a2.cdn-sync-example.com
p9q1z7.cdn-sync-example.com
x4v2n6.cdn-sync-example.com
```

可能原因包括：
- DGA (Domain Generation Algorithm，網域產生演算法)
- tracking identifier
- command lookup
- 將 encoded data 放進 subdomain

DNS tunneling 更可能把資料直接放進 query：

```text
MFRGGZDFMZTWQ2LK.exfil.example.com
```

如果攻擊者控制 `example.com` 的 authoritative DNS，這些 subdomain 最終會送到攻擊者的 DNS infrastructure。

所以一個非常重要的 mental model 是：

**DNS query 本身也是一條 outbound data channel。**

### 7. Detection / Investigation 思路

有價值的 telemetry 包括：

- enterprise recursive resolver logs
- endpoint DNS client telemetry
- firewall / network flow
- EDR (Endpoint Detection and Response，端點偵測與回應)
- proxy logs
- passive DNS
- authoritative DNS logs

值得觀察的 behavior：

**高 query rate**  
單一 endpoint 在短時間大量查詢同一 parent domain。

**高 unique-subdomain ratio**  
同一 base domain 下的 hostname 持續改變。

**高 entropy label**  
subdomain 呈現 random / encoded pattern。

**異常 record type**  
TXT (Text，文字) record 有時被 tunneling 使用，但 SaaS (Software as a Service，軟體即服務) 也大量使用，因此不能單獨當惡意判斷。

**NXDOMAIN spike**  
DGA malware 可能大量查不存在的 domain；但 browser typo、scanner、service discovery 也可能造成類似現象。

**Rare / newly observed domain**  
值得 enrichment，但新 domain 不等於 malicious。

**Process context**  
`chrome.exe` 查 domain 與 `powershell.exe`、Office child process 或未知 binary 查相同 domain，風險意義不同。

成熟 detection 的核心通常是：

**DNS behavior + endpoint process + destination + domain history + baseline**

而不是只靠單一 IOC (Indicator of Compromise，入侵指標)。

### 8. SOC/IR 調查範例

SIEM (Security Information and Event Management，安全資訊與事件管理) 顯示某 workstation 每 30 秒查一個罕見 domain。

可以依序：

1. 找第一次與最後一次 query。
2. 算 frequency、record type、unique subdomain 與 NXDOMAIN ratio。
3. 用 EDR 找是哪個 process 發起查詢。
4. 看 parent/child process、hash、command line、user context。
5. 看解析出的 IP 是否真的建立 TCP/TLS connection。
6. 查其他 endpoint 是否有相同行為。
7. 用 passive DNS / threat intelligence 看 domain 與 infrastructure 歷史。

這裡要注意：DNS 只可能是 discovery 或 beaconing 的第一階段，真正 C2 payload 可能走 HTTPS。

### 9. False Positive 與 limitation

大量 unique subdomain 不等於 tunneling。CDN (Content Delivery Network，內容傳遞網路)、廣告、anti-fraud、cloud telemetry 都可能產生高度動態 hostname。

高 entropy 也可能是 cloud-generated identifier。

DoH 可能讓 network sensor 看不到 query name；cache 則讓 endpoint、resolver、authoritative log 三者看到的事件數量不一致。

因此 DNS detection 非常適合做 correlation 與 anomaly scoring，但不適合用單一「字串長度 > N」規則直接封鎖。

### 10. 防禦與設計 trade-off

企業可以強制 endpoint 使用內部 resolver，以換取 centralized logging、filtering 與 policy enforcement，但 resolver 也因此成為重要 infrastructure dependency。

封鎖所有外部 DNS/DoH 能提高 visibility，但可能破壞應用程式、browser privacy feature 或 cloud service。

DNSSEC 提供 authenticity，但沒有 confidentiality；部署與 key lifecycle 也增加複雜度。

TTL 則是在 freshness、failover、latency 與 server load 之間取捨。

### 11. 與其他概念的連結

DNSSEC 與 TLS (Transport Layer Security，傳輸層安全性) 很適合對比：TLS 保護 client 與 application server 間的 channel 與 server identity；DNSSEC 驗證 DNS data 本身的來源與完整性。

DNS tunneling 與 HTTP C2 的共同點，是攻擊者利用「企業原本就必須允許的 protocol」承載惡意 control/data。

而 DNS cache 也和先前學過的 Kerberos / PAC 有相似的設計精神：

**為了效能與可用性而快取可信資訊，但同時引入 freshness、revocation 與 investigation visibility 的代價。**

### 今天應該記住

1. **Recursive resolver 幫 client 完成查詢；root/TLD 多半提供 referral；authoritative server 才管理 zone data。**
2. **DNSSEC 是 authenticity/integrity，不是 encryption；DoH/DoT 保護 transport。**
3. **DNS query 本身可以成為 C2 或 exfiltration channel。**
4. **DNS detection 應結合 frequency、entropy、NXDOMAIN、domain history 與 process context。**
5. **Cache、TTL 與 encrypted DNS 都是安全、效能、隱私與可見性的 trade-off。**

## 2/4｜CySA：混合雲漏洞掃描判斷

### English original

A company is implementing a vulnerability management program and moving from an on-premises environment to a hybrid IaaS cloud environment. Which of the following implications should be considered on the new hybrid environment?

A. The current scanners should be migrated to the cloud  
B. Cloud-specific misconfigurations may not be detected by the current scanners  
C. Existing vulnerability scanners cannot scan IaaS systems  
D. Vulnerability scans on cloud environments should be performed from the cloud

### 中文完整翻譯

一家公司正在導入漏洞管理計畫，並從內部部署環境移轉到混合式 IaaS (Infrastructure as a Service，基礎設施即服務) 雲端環境。針對新的混合環境，下列哪一項影響是應該考量的？

A. 應將目前的掃描器移轉到雲端  
B. 目前的掃描器可能無法偵測雲端特有的錯誤設定  
C. 現有的漏洞掃描器無法掃描 IaaS 系統  
D. 雲端環境的漏洞掃描應從雲端內部執行

---

### 答案與解析

**正確答案：B. Cloud-specific misconfigurations may not be detected by the current scanners**

#### 為什麼正確

傳統 vulnerability scanner 很擅長找 host / service 層問題，例如缺少 patch、已知 CVE (Common Vulnerabilities and Exposures，常見漏洞與暴露)、弱服務設定與 open port；但 cloud risk 還包含 control plane 與 identity configuration，例如過度寬鬆的 IAM (Identity and Access Management，身分與存取管理) policy、public object storage、security group 與 cloud-native key policy。

如果原 scanner 只理解 OS (Operating System，作業系統) 與 network service，它不一定理解 cloud provider API 暴露的 configuration state。

#### 其他選項為什麼不對

**A. The current scanners should be migrated to the cloud**  
Scanner 放在哪裡不是核心要求；實際架構可能同時使用 on-prem scanner、cloud scanner、agent 與 API-based assessment。

**C. Existing vulnerability scanners cannot scan IaaS systems**  
過度絕對。IaaS VM (Virtual Machine，虛擬機器) 仍可被許多傳統 scanner 掃描，只是未必看得到 cloud control-plane misconfiguration。

**D. Vulnerability scans on cloud environments should be performed from the cloud**  
不一定。掃描位置取決於 reachability、provider policy 與 architecture。

#### CySA / 實務概念

要區分 **workload vulnerability** 與 **cloud configuration risk**。前者偏 VM、package、service；後者偏 identity、storage exposure、network policy 與 managed service configuration。現代環境常結合 vulnerability management 與 CSPM (Cloud Security Posture Management，雲端安全態勢管理)。

#### SOC / IR 記憶點

**把 server 搬到 cloud，不代表原本 scanner 的 coverage 也自動搬過去了。先畫出 control plane、identity plane、data plane，再問每一層誰在看。**

## 3/4｜CySA：惡意程式情報蒐集方式

### English original

A security analyst is performing an investigation involving multiple targeted Windows malware binaries. The analyst wants to gather intelligence without disclosing information to the attackers. Which of the following actions would allow the analyst to achieve the objective?

A. Upload the binary to an air gapped sandbox for analysis  
B. Send the binaries to the antivirus vendor  
C. Execute the binaries on an environment with internet connectivity  
D. Query the file hashes using VirusTotal

### 中文完整翻譯

一名安全分析師正在調查多個具針對性的 Windows 惡意程式 binary。分析師希望蒐集情報，同時不向攻擊者洩漏調查資訊。下列哪一項操作最能達成這個目標？

A. 將 binary 上傳到 air-gapped sandbox（實體／網路隔離沙箱）進行分析  
B. 將 binary 傳送給防毒軟體供應商  
C. 在具有 Internet 連線的環境中執行 binary  
D. 使用 VirusTotal 查詢檔案 hash

---

### 答案與解析

**正確答案：A. Upload the binary to an air gapped sandbox for analysis**

#### 為什麼正確

Air-gapped sandbox 允許 analyst 進行 static / dynamic malware analysis，同時避免 sample 主動連回攻擊者 infrastructure。對 targeted malware 特別重要，因為 malware 可能具有 beaconing、victim fingerprinting、single-use C2 或 operator notification 行為。

#### 其他選項為什麼不對

**B. Send the binaries to the antivirus vendor**  
第三方可能進一步分享、產生 signature 或 cloud analysis；analyst 失去對 sample disclosure 的完整控制。

**C. Execute the binaries on an environment with internet connectivity**  
Malware 可以 beacon、下載下一階段 payload，甚至直接讓 operator 知道 sample 正在被分析。

**D. Query the file hashes using VirusTotal**  
單純 hash lookup 通常比直接 upload sample 的 disclosure 風險低，但 targeted operation 中仍須考慮查詢行為、平台 sharing policy 與 hash 是否已存在。

#### 題庫答案的實務校正

A 在考試語境下合理，但 air-gapped 不代表天然安全。Dynamic analysis 仍需考慮 VM escape、shared folder、clipboard、host-only service 與 sample persistence。

若只需要 reputation enrichment，而且 hash 已是公開已知樣本，hash lookup 可能比把未知 binary 提交給 public service 更合適。實務上應依事件敏感度與 sharing policy 決定。

#### CySA / 實務概念

這是 OPSEC (Operations Security，作業安全) 問題。Malware analysis 不只是「能不能執行」，還要控制分析行為本身會不會改變 adversary behavior。

#### SOC / IR 記憶點

**遇到 targeted malware，先問「我的分析動作會不會讓對方知道我看見它？」再決定是否上傳 public sandbox、查 hash 或允許 Internet egress。**

## 4/4｜CySA：事件後改善流程判斷

### English original

Which of the following is an important aspect that should be included in the lessons-learned step after an incident?

A. Identify any improvements or changes in the incident response plan or procedures  
B. Determine if an internal mistake was made and who did it so they do not repeat the error  
C. Present all legal evidence collected and turn it over to iaw enforcement  
D. Discuss the financial impact of the incident to determine if security controls are well spent

### 中文完整翻譯

在事件發生後的 lessons-learned（經驗教訓）階段，下列哪一項是應該包含的重要內容？

A. 找出事件回應計畫或程序中需要改善或變更的地方  
B. 判斷是否有人員犯下內部錯誤，並確認是誰，以避免該人再次犯錯  
C. 提交所有蒐集到的法律證據，並交給執法機關  
D. 討論事件造成的財務影響，以判斷安全控制是否值得投入

> 原題選項 C 中的 `iaw enforcement` 為題庫原文拼字，語意應為 `law enforcement`；英文原文保留題庫措辭。

---

### 答案與解析

**正確答案：A. Identify any improvements or changes in the incident response plan or procedures**

#### 為什麼正確

Lessons learned 的核心是把 incident 轉成可追蹤的改善：哪些 detection 沒看到、escalation 是否太慢、playbook 是否缺步驟、contact list 是否過期、containment 是否造成額外 impact，以及哪些 control 應調整。

#### 其他選項為什麼不對

**B. Determine if an internal mistake was made and who did it**  
Post-incident review 應優先找 system/process improvement。需要處理 misconduct 時可由 HR (Human Resources，人力資源) 或 management 依程序處理，但「找出誰犯錯」不是 lessons-learned 的核心。

**C. Present all legal evidence and turn it over to law enforcement**  
是否涉及 law enforcement 取決於法律、事件類型與組織決策，不是每次 incident 的必備步驟。

**D. Discuss the financial impact**  
Business impact 可以討論，但選項把目的限縮成判斷 security controls 是否值得投入，並不是 lessons learned 的主要目標。

#### CySA / 實務概念

成熟 post-incident review 應把 observation 轉成 owner、action item 與期限。例如「EDR 沒有 alert」只是 observation；「Detection Engineering 在兩週內加入某 telemetry correlation 並 backtest 30 天」才是可追蹤的改善。

#### SOC / IR 記憶點

**Lessons learned 的成功標準不是會議開完，而是 incident 之後 detection、playbook、architecture 或 operating process 真的發生可驗證的改變。**

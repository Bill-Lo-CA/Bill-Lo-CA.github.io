# 2026-09-25｜每日資安學習

## 1/4｜每日資安小知識：OAuth 2.0 / OIDC 到底在保護什麼？從 Authorization Code、PKCE、state、nonce 到 Token Theft

OAuth 2.0 與 OIDC (OpenID Connect，開放式身分連線) 常被一起提到，但解決的是不同問題。

OAuth 2.0 的核心是 delegated authorization（委派授權）：讓一個 client 在不取得使用者密碼的情況下，取得對特定 resource 的有限存取權。

OIDC 則在 OAuth 2.0 上增加 identity layer，讓 client 可以驗證「使用者是誰」。

簡化 mental model：

**OAuth 2.0：我能代表你做什麼？**

**OIDC：你是誰？**

真正的風險不只是 token 長得像 JWT (JSON Web Token，JSON 網頁權杖)，而是整個授權流程是否被正確綁定：authorization request、redirect URI、authorization code、token audience、browser session、refresh token 都可能成為攻擊面。

### 1. OAuth 2.0 解決什麼問題？

假設第三方行事曆工具要讀你的雲端 Calendar。

舊式做法可能要求你直接把帳號密碼給第三方。這會造成：

- client 必須保存密碼
- 無法限制權限 scope
- 難以只撤銷單一應用程式
- password rotation 會破壞 integration
- client 被入侵時可能直接暴露主帳號 credential

OAuth 2.0 改成：

1. client 將使用者導向 Authorization Server。
2. 使用者在 Authorization Server 登入。
3. 使用者或管理政策決定 consent / scope。
4. Authorization Server 發出受限 token。
5. client 用 token 存取 Resource Server。

因此 client 不需要知道使用者密碼。

### 2. 四個主要角色

OAuth 2.0 常見角色：

- **Resource Owner**：通常是使用者。
- **Client**：希望存取資源的應用程式。
- **Authorization Server**：負責登入、同意與發 token。
- **Resource Server**：真正提供 API 或 resource 的服務。

例如 Calendar integration：

- Resource Owner：使用者
- Client：第三方 Calendar App
- Authorization Server：Identity Provider
- Resource Server：Calendar API

這些是邏輯角色，不一定對應不同實體主機。

### 3. Authorization Code Flow 為什麼重要？

Authorization Code Flow 不直接把長效 token 暴露在 browser-facing redirect 中。

大致流程：

1. Browser 前往 Authorization Server 的 authorize endpoint。
2. 使用者登入並完成 consent。
3. Authorization Server redirect 回 client，帶回短效 authorization code。
4. Client 再向 token endpoint 用 code 換 Access Token。
5. Client 使用 Access Token 存取 Resource Server。

Authorization Code 通常具有：

- 短效
- 單次使用
- client context 綁定
- redirect URI 綁定

這個設計把 front channel 與 back channel 分開。

如果直接把 token 放 URL，更容易出現在：

- browser history
- proxy log
- analytics
- Referer
- screenshot
- malicious extension

### 4. PKCE 解決什麼？

PKCE (Proof Key for Code Exchange，授權碼交換證明金鑰) 主要防止 authorization code interception。

Public client，例如 mobile app，通常無法安全保存 client secret。

PKCE 流程：

1. Client 產生高 entropy 的 code_verifier。
2. 將它做雜湊轉換形成 code_challenge。
3. Authorization request 帶上 code_challenge。
4. Authorization Server 發 authorization code。
5. Client 到 token endpoint 時提交原始 code_verifier。
6. Server 驗證 verifier 是否能對應最初的 challenge。

常見概念是：

**code_challenge = BASE64URL(SHA256(code_verifier))**

SHA-256 (Secure Hash Algorithm 256-bit，256 位元安全雜湊演算法) 並不是用來加密 verifier，而是讓 Authorization Server 能確認：「來交換 code 的 client，是否持有當初發起 flow 時的秘密隨機值。」

即使 attacker 攔到 authorization code，沒有 verifier 仍無法換 token。

### 5. state 是什麼？

state 常用來防止 OAuth flow 中的 CSRF (Cross-Site Request Forgery，跨站請求偽造) 與 response/session 混淆。

Client 開始授權流程時，建立一個高 entropy state，並把它與目前 browser session 綁定。

Redirect 回來後，client 必須確認 response 中的 state 與 session 中原值一致。

因此 state 的核心是：

**把 authorization response 綁回最初發起 request 的 browser/client session。**

### 6. OIDC 的 nonce 又是什麼？

OIDC 引入 ID Token。

ID Token 常包含：

- iss：issuer
- sub：subject
- aud：audience
- exp：expiration
- iat：issued at
- nonce

nonce 主要將 ID Token 綁定到特定 authentication request，降低 replay 或 response substitution。

可以這樣記：

- **state**：這個 authorization response 是不是屬於我這個 session / flow？
- **nonce**：這個 ID Token 是不是屬於我這次 authentication request？

兩者可能一起出現，但目的不同。

### 7. Access Token 與 ID Token 不能混用

**Access Token** 是給 Resource Server 使用。

**ID Token** 是給 Client 驗證 authentication result。

如果 API 把 ID Token 當 Access Token 使用，可能造成：

- audience validation 錯誤
- scope enforcement 錯誤
- token intended-purpose 混淆

Mental model：

**ID Token 說「這個使用者是誰」。**

**Access Token 說「這個 client 能對 resource 做什麼」。**

### 8. JWT signature 到底保護什麼？

很多 ID Token 或 Access Token 會使用 JWT。

JWT 常見邏輯結構：

**header.payload.signature**

Signature 提供的是 integrity，以及在信任 signing key 的前提下驗證 issuer。

但 signature 不代表 payload 被加密。

一般 signed JWT 的 payload 通常任何持有者都能 decode，因此不能因為「有簽章」就把敏感秘密任意放進去。

Server 驗 JWT 時至少要看：

- signature
- issuer
- audience
- expiration
- not-before
- algorithm policy
- token type / intended use

### 9. audience 為什麼重要？

假設 token 的 audience 是 calendar-api。

如果 attacker 把它拿去 payment-api，而 payment-api 只驗 signature、不驗 audience，就可能接受根本不是發給自己的 token。

所以：

**Signature 回答：誰簽的、內容有沒有被改。**

**Audience 回答：這顆 token 是不是發給我。**

### 10. redirect URI 為什麼是高風險欄位？

Authorization Server 最後要把 browser 導回 client callback。

如果 redirect URI 驗證太寬鬆，例如 wildcard，且 client 又有 open redirect，可能形成：

Authorization Server → client open redirect → attacker-controlled site

結果 authorization code 可能被洩漏。

因此 redirect URI 通常應：

- 預先註冊
- 精確比對
- 避免 wildcard
- 避免可利用的 open redirect

### 11. Refresh Token 為什麼更敏感？

Access Token 常是短效。

Refresh Token 可以取得新的 Access Token，所以通常代表更長的 session continuity。

簡化：

**偷到 Access Token = 短期 session hijack。**

**偷到 Refresh Token = 可能長期維持 access。**

常見防禦：

- refresh token rotation
- reuse detection
- sender-constrained token
- device binding
- revocation
- risk-based session evaluation

Refresh Token Rotation 的想法是每次 refresh 都換一顆新 token，舊 token 立即失效。若舊 token 再被使用，可能表示 token 被複製，系統可以 revoke 整個 token family。

### 12. 攻防情境：Authorization Code 被攔截

假設 mobile app 使用 custom URI scheme：

myapp://callback

若 malicious app 也能註冊相同 scheme，它可能攔到：

myapp://callback?code=ABC123

如果沒有 PKCE，attacker 可能直接拿 code 去 token endpoint 換 token。

如果有 PKCE，attacker 還必須取得原 client process 持有的 code_verifier。

這就是 PKCE 的直接攻防價值。

### 13. Consent Phishing：完全可以不偷密碼

傳統 phishing 想偷 password。

Consent phishing 則讓使用者自己授權惡意 OAuth application，例如：

- Mail.Read
- Files.ReadWrite.All
- offline_access

使用者甚至可能：

- 在真正的 Identity Provider 頁面登入
- 完成真正的 MFA (Multi-Factor Authentication，多因素驗證)
- 完全沒把密碼輸入 attacker 網站

但最後 attacker 仍取得 delegated permission。

因此 MFA 並不能單獨解決 OAuth application abuse。

還需要：

- application consent policy
- verified publisher
- admin approval
- least-privilege scope
- OAuth app monitoring

### 14. Detection / Investigation：SOC 應看什麼？

重要 telemetry 包括：

#### Identity Provider Logs

觀察：

- authorization event
- token issuance
- refresh token usage
- consent event
- MFA
- client ID
- redirect URI
- source IP
- device / browser context

#### Application / API Logs

觀察：

- subject / user
- client ID
- scope
- audience
- API action
- source IP
- user agent

#### Endpoint Telemetry

觀察：

- browser cookie / token cache theft
- suspicious extension
- process reading browser storage
- token cache access
- unusual OAuth device-flow interaction

### 15. 可疑行為

**New OAuth application consent**

使用者突然授權陌生 client 高敏感 scope。

**Token usage from unusual geography**

短時間由遠距地理位置使用相同 session。要注意 VPN (Virtual Private Network，虛擬私人網路)、mobile carrier 與 cloud proxy 可能造成 false positive。

**Long-lived API activity without expected interactive login**

可能是正常 refresh flow，也可能是 stolen refresh token。

**New client ID / unusual scope**

使用者平常只用官方 client，突然由陌生 application 要求大量 mail/file permission。

### 16. False Positive 與 limitation

OAuth telemetry 很容易被合法 SaaS (Software as a Service，軟體即服務) 淹沒：

- background sync
- mobile app
- email client
- CI/CD (Continuous Integration / Continuous Delivery，持續整合／持續交付) integration
- backup tool

因此「沒有 interactive login 但有 token use」不能直接判 malicious。

NAT (Network Address Translation，網路位址轉換)、VPN、cloud proxy 也會降低 geolocation 的可靠性。

成熟偵測要建立 identity baseline：

- user 常用 client ID
- device
- geography
- scope
- API behavior
- token lifetime
- consent history

### 17. 防禦與設計 trade-off

Short-lived token：

- token theft window 較短
- 但 refresh 頻率更高

Long-lived token：

- user experience 與 offline app 較方便
- 但 stolen-token impact 更大

Strict redirect URI：

- 安全
- 但 deployment / multi-environment configuration 更麻煩

PKCE：

- 增加 flow complexity
- 但大幅降低 authorization-code interception risk

Centralized IdP (Identity Provider，身分提供者)：

- 統一 visibility 與 policy
- 但 IdP 本身也成為高價值 infrastructure

### 18. 與其他概念的連結

#### 與 Kerberos

Kerberos ticket 與 OAuth token 都是在把 authentication / authorization context 帶給 service。

不同點在於：

- Kerberos 偏 enterprise service authentication / ticketing
- OAuth 偏 delegated authorization / web API ecosystem

共同核心是：**token 不是看到就信，還要驗 issuer、target、lifetime 與 context。**

#### 與 JWT

JWT 是 token format，不是 OAuth 本身。

OAuth 完全可以使用 opaque token；OIDC ID Token 通常是 JWT。

因此不能把 OAuth 與 JWT 畫等號。

#### 與 Zero Trust

Zero Trust 不只是登入時做 MFA。

成熟設計還會考慮：

- token lifetime
- device
- risk
- scope
- audience
- session revocation

### 今天應該記住

1. **OAuth 2.0 是 delegated authorization；OIDC 才增加 authentication / identity layer。**
2. **PKCE 防 authorization-code interception；state 綁 flow/session；nonce 綁 OIDC authentication request。**
3. **Access Token 給 Resource Server；ID Token 給 Client，兩者用途不能混用。**
4. **JWT 不能只驗 signature，還要驗 issuer、audience、expiration 與 intended use。**
5. **Consent phishing 可以完全不偷 password，因此 MFA 不是 OAuth app abuse 的完整防線。**

## 2/4｜CySA：Zero Trust 優先順序判斷

### English original

The Chief Information Security Officer is directing a new program to reduce attack surface risks and threats as part of a zero trust approach. The IT security team is required to come up with priorities for the program. Which of the following is the best priority based on common attack frameworks?

A. Reduce the administrator and privileged access accounts  
B. Employ a network-based IDS  
C. Conduct thorough incident response  
D. Enable SSO to enterprise applications

### 中文完整翻譯

CISO (Chief Information Security Officer，資訊安全長) 正在推動一項新的計畫，作為 Zero Trust（零信任）方法的一部分，以降低 attack surface（攻擊面）風險與威脅。IT (Information Technology，資訊技術) security team 必須為此計畫設定優先事項。根據常見 attack framework，下列哪一項最適合作為優先事項？

A. 減少 administrator 與 privileged access accounts（高權限帳號）的數量  
B. 部署 network-based IDS (Intrusion Detection System，入侵偵測系統)  
C. 執行完整的 incident response（事件回應）  
D. 對 enterprise applications 啟用 SSO (Single Sign-On，單一登入)

---

### 答案與解析

**正確答案：A. Reduce the administrator and privileged access accounts**

#### 為什麼正確

Privileged account 是 attacker 最有價值的目標之一。

如果組織存在大量：

- local administrator
- domain administrator
- standing privilege
- shared admin account
- overly broad service account

一旦 credential 被竊取，lateral movement 與 privilege escalation 空間就很大。

Zero Trust 的核心之一是 least privilege（最小權限），因此減少不必要的 persistent privileged access 能直接縮小 attack surface。

#### 其他選項為什麼不對

**B. Employ a network-based IDS**  
IDS 能提升 detection，但不直接減少 privileged attack surface。

**C. Conduct thorough incident response**  
Incident Response 很重要，但主要提升事件後的 response capability，不是首先降低 attack surface。

**D. Enable SSO to enterprise applications**  
SSO 可以改善 authentication management，但如果沒有強 MFA、conditional access 與 session control，也會集中 identity blast radius。

#### CySA / 實務概念

實務可以進一步使用：

- JIT (Just-In-Time，即時) privilege
- PAM (Privileged Access Management，特權存取管理)
- separate admin accounts
- privileged workstation
- temporary elevation

#### SOC / IR 記憶點

**減少 standing privilege，比多看一條告警更直接縮小 attacker 成功登入後的活動空間。**

## 3/4｜CySA：CVSS 向量判讀

### English original

Given the following CVSS string:

CVSS:3.0/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H

Which of the following attributes correctly describes this vulnerability?

A. A user is required to exploit this vulnerability.  
B. The vulnerability is network based.  
C. The vulnerability does not affect confidentiality.  
D. The complexity to exploit the vulnerability is high.

### 中文完整翻譯

給定以下 CVSS (Common Vulnerability Scoring System，通用漏洞評分系統) 向量：

CVSS:3.0/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H

下列哪一項描述正確？

A. 利用此漏洞需要使用者互動。  
B. 此漏洞屬於 network-based（可透過網路利用）。  
C. 此漏洞不影響 confidentiality（機密性）。  
D. 此漏洞的 exploit complexity（利用複雜度）很高。

---

### 答案與解析

**正確答案：B. The vulnerability is network based.**

#### 為什麼正確

AV:N 表示 AV (Attack Vector，攻擊向量) = Network。

因此 attacker 可以透過 network path 觸發漏洞，不需要 local 或 physical access。

完整拆解：

- AV:N = Attack Vector: Network
- AC:L = Attack Complexity: Low
- PR:N = Privileges Required: None
- UI:N = User Interaction: None
- S:U = Scope: Unchanged
- C:H = Confidentiality Impact: High
- I:H = Integrity Impact: High
- A:H = Availability Impact: High

#### 其他選項為什麼不對

**A. A user is required to exploit this vulnerability**  
錯。UI:N 表示 User Interaction: None。

**C. The vulnerability does not affect confidentiality**  
錯。C:H 表示 Confidentiality Impact: High。

**D. The complexity to exploit the vulnerability is high**  
錯。AC:L 表示 Attack Complexity: Low。

#### CySA / 實務概念

不要只背 CVSS 分數，而要會直接讀 vector。

尤其先看：

- AV
- AC
- PR
- UI

這四項快速描述 exploitability。

再看：

- C
- I
- A

理解 impact。

#### 題庫答案校正

題庫答案 B 正確。

但實務優先順序不能只看 Base Score，還要考慮：

- exploit 是否公開
- 是否正在 exploited in the wild
- asset exposure
- business criticality
- compensating controls
- reachable attack path

#### SOC / IR 記憶點

**看到 CVSS vector，先翻成一句話：Remote？Low complexity？No privilege？No click？Impact 多大？這比只記 9.8 更實用。**

## 4/4｜CySA：鑑識證據保存判斷

### English original

An employee is suspected of misusing a company-issued laptop. The employee has been suspended pending an investigation by human resources. Which of the following is the best step to preserve evidence?

A. Disable the user’s network account and access to web resources.  
B. Make a copy of the files as a backup on the server.  
C. Place a legal hold on the device and the user’s network share.  
D. Make a forensic image of the device and create a SHA-1 hash.

### 中文完整翻譯

一名員工被懷疑不當使用公司配發的 laptop。該員工已被停職，等待 HR (Human Resources，人力資源) 進行調查。下列哪一項是保存證據的最佳步驟？

A. 停用該使用者的 network account 與 web resource access。  
B. 將檔案複製到 server 作為 backup。  
C. 對該裝置與使用者 network share 設置 legal hold（法律保全）。  
D. 對該裝置建立 forensic image（鑑識映像），並產生 SHA-1 hash。

---

### 答案與解析

**正確答案：D. Make a forensic image of the device and create a SHA-1 hash.**

#### 為什麼正確

Forensic image 的目的，是建立可重複分析的 bit-level copy，避免直接在 original evidence 上反覆操作。

Hash 用來確認 acquisition 後的 image 是否被修改。

核心證據原則：

- preserve original
- analyze copy
- document handling
- verify integrity

因此 forensic image + hash 是選項中最直接的 evidence preservation 方法。

#### 其他選項為什麼不對

**A. Disable the user’s network account and access to web resources**  
這是 containment / access control，不是保存 laptop 內容。

**B. Make a copy of the files as a backup on the server**  
一般 file copy 不會完整保存：

- deleted-file artifact
- unallocated space
- filesystem metadata
- slack space
- partition structure

因此不能取代 forensic image。

**C. Place a legal hold on the device and the user’s network share**  
Legal hold 在 litigation / HR investigation 中非常重要，可以阻止 retention policy 或 routine deletion 清除 evidence。但若題目聚焦「如何保存 laptop 的實際證據內容」，forensic imaging 更直接。

#### 題庫答案的實務校正

題庫使用 SHA-1 (Secure Hash Algorithm 1，安全雜湊演算法 1)。

SHA-1 已不適合新的 collision-resistant security design，因為 collision attack 已實際存在。

因此考試答案仍是 D，但現代實務通常更偏好：

**SHA-256 + documented chain of custody**

而不是只依賴 SHA-1。

#### CySA / 實務概念

Evidence preservation 還包含：

- chain of custody
- evidence identifier
- acquisition time
- acquisition tool
- source device
- analyst
- write blocker
- original / working copy separation
- secure storage

#### SOC / IR 記憶點

**Backup 是為了恢復資料；forensic image 是為了保存證據。兩者目的不同。**

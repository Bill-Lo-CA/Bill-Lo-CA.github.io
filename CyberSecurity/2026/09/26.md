# 2026-09-26｜每日資安學習

## 1/4｜每日資安小知識：Email Security 深入理解——SPF、DKIM、DMARC 到底各自驗證什麼？

Email 是企業最常見的初始攻擊入口之一，但很多人把 SPF、DKIM、DMARC 當成三個「防釣魚設定」一起背，卻沒有拆開理解每一層到底在驗什麼。

真正的核心問題是：SMTP 本身原本沒有提供強制的寄件者身分驗證。

SMTP (Simple Mail Transfer Protocol，簡單郵件傳輸協定) 的設計年代很早，最初假設網路上的 mail server 大致可信。因此寄件者欄位、mail envelope 與 message header 可以被不同程度地偽造。

現代 email authentication 的核心，就是在這個原本沒有內建強身分驗證的系統上，逐層增加 domain-based trust。

### 1. 一封 Email 其實有不只一個寄件者

使用者在郵件客戶端看到的是 Header From，例如：

From: ceo@example.com

但 SMTP 傳輸過程還有 Envelope From，也就是 MAIL FROM / Return-Path 使用的寄件身分。

兩者不是同一個欄位。

簡化來看：

- Header From：使用者通常看到的寄件者。
- Envelope From / Return-Path：SMTP routing 與 bounce handling 使用。
- HELO / EHLO domain：SMTP server 自我介紹時使用的名稱。

攻擊者可以讓 Header From 看起來是 CEO <ceo@company.com>，但實際傳輸來自完全不同的 domain。

所以只看畫面上的 From 無法判斷真實來源。

### 2. SPF 驗證的是什麼？

SPF (Sender Policy Framework，寄件者政策框架) 解決的是：

**這個來源 IP 是否被某個 domain 授權可以替它寄信？**

Domain owner 在 DNS (Domain Name System，網域名稱系統) TXT record 中發布 SPF policy。

Receiving mail server 收到信件時，會看實際 SMTP connection source IP，再比對 Envelope From domain 的 SPF record。

因此 SPF 驗的是：

**source IP ↔ envelope domain authorization**

而不是直接驗證使用者看到的 Header From。

### 3. 為什麼 SPF 不能單獨阻止 From spoofing？

假設 attacker 控制 evil.example。

它可以正確設定自己的 SPF，使 attacker IP 對 evil.example 驗證成功。

SMTP envelope 使用 attacker@evil.example，但 Header From 卻可以寫成 payroll@company.com。

此時 SPF 仍可能 PASS，因為 SPF 驗的是 evil.example，而不是 company.com 的 visible Header From。

因此：

**SPF PASS 不等於使用者看到的寄件者是真的。**

DMARC 後面會利用 alignment 解決這個 gap。

### 4. DKIM 又在驗什麼？

DKIM (DomainKeys Identified Mail，網域金鑰識別郵件) 解決的是另一個問題：

**這封 message 的某些 header/body 是否由某個 domain 的 private key 簽過，而且傳輸途中沒有被修改？**

寄件 mail system 會對 message 建立 cryptographic signature，並在 DKIM-Signature header 中放入 signing domain 與 selector。

其中 d= 表示 signing domain；s= 表示 selector。

Receiver 會到 DNS 查 selector._domainkey.example.com 取得 public key，再驗證 signature。

所以 DKIM 建立的是：

**message integrity + signing-domain authentication**

### 5. DKIM 為什麼需要 selector？

Domain 不希望永遠只使用一把 DKIM key。

Selector 讓同一 domain 可以同時發布多把 key，這樣可以：

- key rotation
- 不同 mail provider 使用不同 key
- 分離 marketing / corporate mail infrastructure
- migration 時同時保留新舊 key

這和 TLS certificate lifecycle 類似：key management 本身就是安全設計的一部分。

### 6. DKIM 也不是寄件者本人簽名

DKIM 常常是 mail platform 在 server side 自動簽。

因此 DKIM PASS 通常代表：

**這封信經過了被該 domain 授權使用 DKIM private key 的 mail system。**

它不一定代表：

**From 裡顯示的某個人親自做了 digital signature。**

DKIM 是 domain-level authentication，不是 user-level non-repudiation。

### 7. DMARC 在 SPF / DKIM 上增加了什麼？

DMARC (Domain-based Message Authentication, Reporting and Conformance，網域型郵件驗證、報告與一致性) 的核心價值是：

1. 把 authentication 結果和 Header From domain 對齊。
2. 讓 domain owner 宣告 fail 時應如何處理。
3. 提供 reporting。

真正的關鍵字是 alignment。

DMARC 不只是問 SPF pass 嗎、DKIM pass 嗎，而是問：

**通過驗證的 domain，有沒有和使用者看到的 Header From domain 對得起來？**

### 8. SPF Alignment

假設 Header From 是 payroll@company.com，Envelope From 也是 bounce@company.com。

SPF 通過 company.com，且 Header From 也是 company.com，這就是 SPF aligned。

但如果 Header From 是 payroll@company.com，Envelope From 卻是 bounce@evil.example，即使 evil.example 的 SPF PASS，也沒有和 company.com alignment。

因此 DMARC 不會把它當成有效的 SPF-authenticated company.com message。

### 9. DKIM Alignment

假設 Header From 是 payroll@company.com，DKIM signing domain d=company.com。

DKIM 驗證成功，而且 signing domain 與 Header From domain alignment。

如果 Header From 是 payroll@company.com，但 DKIM d=mailer-vendor.example，DKIM 本身可以 PASS，但對 DMARC 而言是否 aligned 要看 domain relationship 與 policy。

這也是 SaaS (Software as a Service，軟體即服務) mail provider configuration 常出問題的地方。

### 10. DMARC 的核心判斷

簡化 mental model：

**DMARC PASS = 至少一條 aligned authentication path 成功。**

也就是：

- SPF PASS + SPF alignment

或：

- DKIM PASS + DKIM alignment

不要求兩個都成功。

### 11. DMARC policy

Domain owner 可以發布 DMARC DNS record。

常見 policy：

- p=none：監控，不要求 receiver 隔離或拒收。
- p=quarantine：建議隔離。
- p=reject：建議拒收。

企業通常不應一開始就直接上 reject。

比較安全的導入方式是：

1. p=none
2. 收集 report
3. 找出 legitimate sender
4. 修正 SPF / DKIM
5. 漸進到 quarantine
6. 最後才 reject

### 12. 為什麼 p=none 還有價值？

p=none 不阻擋 spoofing，但可以取得 telemetry。

DMARC aggregate report 可以幫助 domain owner 發現：

- 哪些 IP 正在替 domain 寄信
- 哪些 provider SPF / DKIM misconfigured
- 哪些 source 疑似 spoofing
- 哪些 legacy system 被遺漏

所以 p=none 是 deployment discovery phase，不代表完全沒用。

### 13. Forwarding 為什麼會破壞 SPF？

假設 sender → forwarder → recipient。

原始 sender IP 本來是 SPF 授權來源，但 recipient 最後看到的 SMTP connection source 變成 forwarder IP。

如果 forwarder IP 不在原 sender domain 的 SPF record，SPF 可能 FAIL。

這不是 attacker，而是 mail forwarding 的結構性問題。

因此 DKIM 在 forwarding 情境往往更有韌性，因為只要 message 被轉寄時沒有破壞被簽署內容，signature 仍可能有效。

### 14. Mailing List 為什麼又會破壞 DKIM？

Mailing list 可能修改：

- Subject
- footer
- body
- sender

如果修改了 DKIM-covered content，DKIM signature 可能 FAIL。

所以現實世界中 SPF 與 DKIM 都會遇到 legitimate transformation。

Email authentication 不是一個設好就永遠零誤判的系統。

### 15. ARC 是為了解決什麼？

ARC (Authenticated Received Chain，驗證接收鏈) 的目的，是讓 trusted intermediary 可以保存前一跳看到的 authentication result。

例如 mailing list 收到原始郵件時看到 SPF PASS、DKIM PASS、DMARC PASS；之後 mailing list 修改 message，造成最終 recipient 看起來 DKIM FAIL。

ARC 可以讓中介節點以 cryptographic chain 傳遞「我收到它時，它原本是驗證成功的」。

但 ARC 不是讓所有 forwarding 自動變可信。

Receiver 仍要決定是否信任 ARC signer。

### 16. 攻防情境：CEO Fraud

Attacker 寄出：

From: CEO <ceo@company.com>

但 SMTP envelope 實際是 attacker@evil.example，來源 IP 也屬於 attacker infrastructure。

結果可能是：

- SPF：PASS for evil.example
- DKIM：PASS for evil.example
- Header From：company.com
- DMARC：FAIL because neither path aligns with company.com

如果 company.com policy 是 p=reject，receiver 可以拒收。

這就是 DMARC 對 direct-domain spoofing 的主要價值。

### 17. 但 DMARC 擋不住 lookalike domain

Attacker 也可以註冊 cornpany.com，其中 rn 看起來像 m；或註冊 company-payments.com。

攻擊者可以替自己的 domain 完整設定：

- SPF PASS
- DKIM PASS
- DMARC PASS

因為它確實擁有那個 domain。

所以 email authentication 解決的是：

**你有沒有冒用我的 domain？**

不是：

**你的 domain 看起來是不是故意模仿我？**

Lookalike domain 還需要：

- domain reputation
- lexical similarity
- newly registered domain detection
- brand monitoring
- user awareness
- secure email gateway

### 18. Display Name Spoofing 又是另一層

攻擊者可以寄：

From: "Company CEO" <attacker@gmail.com>

SPF / DKIM / DMARC 可能全部合法 PASS，因為 gmail.com 是真的。

但 display name 還是騙人的。

因此偵測不能只依 email authentication。

### 19. SOC 應該收哪些 telemetry？

SOC (Security Operations Center，安全營運中心) 調查 email 時有價值的 artifacts 包括：

- full message headers
- Authentication-Results
- Received chain
- Return-Path
- Message-ID
- DKIM-Signature
- SPF result
- DMARC result
- source IP
- URLs
- attachment hash
- mail gateway verdict
- mailbox audit log

Authentication-Results 常會同時看到 spf=pass、dkim=pass、dmarc=fail。

這並不矛盾。

它通常表示 SPF / DKIM 對自己的 domain 通過，但沒有和 visible Header From alignment。

### 20. Investigation：不要只看 From

收到 phishing report 後，可以依序：

1. 保存原始郵件，不要只看 screenshot。
2. 找最上游可信 Received header。
3. 確認 source IP。
4. 看 Return-Path / Envelope From。
5. 看 Header From。
6. 看 SPF result。
7. 看 DKIM signing domain 與 signature。
8. 看 DMARC alignment。
9. 分析 URL / attachment。
10. 查 organization 中是否有其他收件人。

Header chain 的信任也有方向性。

Attacker 可以自行加入假的 Received header，但 trusted mail gateway 加上的 header 才能作為較可靠的邊界。

### 21. Detection Engineering

可以建立 composite detection，例如：

- DMARC fail
- visible From 是 internal domain
- source IP 不屬於 approved mail infrastructure
- display name 是 executive
- attachment / URL reputation 可疑
- Reply-To 與 From 不一致

單一特徵通常 false positive 高，但 combination 很強。

### 22. Reply-To 為什麼也值得看？

Attacker 可能使用合法寄信平台，Header From 甚至看起來合理，但 Reply-To 指向 attacker-controlled domain。

目的是讓 victim 按 Reply 後，把對話送到 attacker。

因此 From、Return-Path、Reply-To 三者之間的 relationship 很值得看。

### 23. False Positive 與 limitation

常見 legitimate 問題：

- forwarding
- mailing list
- third-party marketing platform
- CRM (Customer Relationship Management，客戶關係管理) system
- ticketing platform
- newsletter vendor
- HR platform

如果 company.com 開啟 p=reject 卻沒先 inventory 所有 legitimate sender，可能導致正常郵件被拒。

因此 email authentication 是典型的 security / compatibility trade-off。

### 24. 與其他概念的連結

#### DNS

SPF、DKIM、DMARC 都依賴 DNS 發布 policy 或 key。

如果 DNS management 被攻擊，email identity control 也可能受影響。

#### PKI

PKI (Public Key Infrastructure，公開金鑰基礎設施) 與 DKIM 都使用 public/private key cryptography。

但 DKIM public key 通常直接透過 DNS selector 發布，不使用傳統 X.509 certificate chain。

#### OAuth

Email account 本身也常透過 OAuth 2.0 / OIDC (OpenID Connect，開放式身分連線) 登入。

即使 domain authentication 完美，如果 attacker 已經竊取真正 mailbox 的 OAuth token，信件會從真正 tenant 寄出，而且 SPF、DKIM、DMARC 都可能正常 PASS。

所以：

**Email authentication 可以防 spoofed domain，但不能證明 mailbox account 沒被 compromise。**

這也是 SOC 必須把 mail telemetry 與 identity telemetry 串起來的原因。

### 今天應該記住

1. **SPF 驗的是 source IP 是否被 envelope domain 授權，不是 visible Header From。**
2. **DKIM 驗的是 message signature 與 signing domain，不等於某位使用者親自簽名。**
3. **DMARC 的核心是 alignment：SPF 或 DKIM 至少有一條成功且與 Header From 對齊。**
4. **SPF / DKIM / DMARC 可以防 direct-domain spoofing，但擋不住 lookalike domain、display-name spoofing 或真正 mailbox compromise。**
5. **Email investigation 應把 Authentication-Results、Received、Return-Path、From、Reply-To、URL、attachment 與 identity logs 一起看。**

## 2/4｜CySA：威脅情報來源判斷

### English original

An analyst has been asked to validate the potential risk of a new ransomware campaign that the Chief Financial Officer read about in the newspaper. The company is a manufacturer of a very small spring used in the newest fighter jet and is a critical piece of the supply chain for this aircraft. Which of the following would be the best threat intelligence source to learn about this new campaign?

A. Information sharing organization  
B. Blogs/forums  
C. Cybersecurity incident response team  
D. Deep/dark web

### 中文完整翻譯

一名 analyst 被要求驗證一個新 ransomware（勒索軟體）攻擊活動可能帶來的風險。CFO (Chief Financial Officer，財務長) 在報紙上讀到這個攻擊活動。該公司製造最新型戰鬥機所使用的一個非常小的彈簧，而且是該飛機 supply chain（供應鏈）的關鍵一環。下列哪一種 threat intelligence（威脅情報）來源最適合用來了解這個新的攻擊活動？

A. Information sharing organization（資訊共享組織）  
B. Blogs/forums（部落格／論壇）  
C. Cybersecurity incident response team（資安事件回應團隊）  
D. Deep/dark web（深網／暗網）

---

### 答案與解析

**正確答案：A. Information sharing organization**

#### 為什麼正確

題目特別指出公司屬於高敏感、關鍵性的 defense supply chain。

Information sharing organization，例如特定產業的 ISAC (Information Sharing and Analysis Center，資訊共享與分析中心) 或 ISAO (Information Sharing and Analysis Organization，資訊共享與分析組織)，通常能提供：

- sector-specific threat intelligence
- peer organization observations
- adversary TTPs (Tactics, Techniques, and Procedures，戰術、技術與程序)
- targeted campaign information
- trusted sharing context

相比一般公開來源，這類情報更可能與同產業、同供應鏈面臨的真實威脅直接相關。

#### 其他選項為什麼不對

**B. Blogs/forums**  
可以提供很快的公開情報，但品質、時效與可信度差異很大，而且未必針對 defense supply chain。

**C. Cybersecurity incident response team**  
CSIRT (Computer Security Incident Response Team，電腦安全事件回應團隊) 可以分析事件，但它本身不一定是取得 sector-wide campaign intelligence 的最佳來源。

**D. Deep/dark web**  
暗網可以找到 threat actor discussion、leak site 或 criminal marketplace，但情報需要大量 validation，而且題目要求的是最適合企業驗證 campaign risk 的來源，不是最隱密的來源。

#### CySA / 實務概念

Threat intelligence source 的價值不只在「有沒有最新消息」，還在：

- relevance
- reliability
- timeliness
- specificity
- actionability

對 aerospace、finance、healthcare 等特定產業，sector-sharing organization 通常比泛用新聞更有上下文。

#### SOC / IR 記憶點

**情報來源不是越秘密越好；最有價值的是與你的產業、資產與 adversary profile 最相關，而且可被驗證的來源。**

## 3/4｜CySA：Web Server 信任問題判斷

### English original

A virtual web server in a server pool was infected with malware after an analyst used the internet to research a system issue. After the server was rebuilt and added back into the server pool, users reported issues with the website, indicating the site could not be trusted. Which of the following is the most likely cause of the server issue?

A. The server was configured to use SSL to securely transmit data.  
B. The server was supporting weak TLS protocols for client connections.  
C. The malware infected all the web servers in the pool.  
D. The digital certificate on the web server was self-signed.

### 中文完整翻譯

一台位於 server pool 中的 virtual web server，在 analyst 使用 Internet 查詢系統問題後感染了 malware（惡意程式）。該伺服器重建並重新加入 server pool 後，使用者回報網站出現問題，瀏覽器顯示該網站不受信任。下列哪一項最可能造成這個問題？

A. Server 設定成使用 SSL (Secure Sockets Layer，安全通訊端層) 安全傳輸資料。  
B. Server 支援較弱的 TLS (Transport Layer Security，傳輸層安全性) protocol 供 client connection 使用。  
C. Malware 感染了 pool 中所有 web servers。  
D. Web server 上的 digital certificate（數位憑證）是 self-signed（自我簽署）的。

---

### 答案與解析

**正確答案：D. The digital certificate on the web server was self-signed.**

#### 為什麼正確

重建 server 時，如果新 certificate 是自行產生的 self-signed certificate，而 client trust store 中沒有信任它的 root / issuer，browser 就會顯示 certificate not trusted、unknown issuer 或 connection not private。

題目特別描述的是「site could not be trusted」，最直接指向 certificate trust-chain 問題。

#### 其他選項為什麼不對

**A. The server was configured to use SSL to securely transmit data.**  
單純啟用加密傳輸不是造成 certificate untrusted 的原因。題目使用 SSL 這個舊稱，但問題核心是 certificate trust。

**B. The server was supporting weak TLS protocols for client connections.**  
弱 TLS protocol 可能導致 security warning、policy block 或 downgrade risk，但不等同於典型的 certificate issuer 不受信任。

**C. The malware infected all the web servers in the pool.**  
題目沒有提供其他 server 被感染的證據，而且 malware infection 本身不直接解釋 browser 為什麼認為 site certificate 不可信。

#### CySA / 實務概念

TLS server authentication 依賴 certificate chain。

典型 chain 是：

Server Certificate → Intermediate Certificate Authority → Root Certificate Authority

CA (Certificate Authority，憑證授權機構) 的 root certificate 必須位於 client trust store 中，或能建立到受信 root 的有效 chain。

Self-signed certificate 沒有外部 trusted CA 為它背書，所以 public-facing service 通常會觸發 trust warning。

#### SOC / IR 記憶點

**TLS 有開和 TLS 身分可信是兩回事。Encryption 保護 channel；certificate chain 建立 peer identity trust。**

## 4/4｜CySA：Web Log 中的 LFI 跡象判斷

### English original

A security analyst discovers an LFI vulnerability that can be exploited to extract credentials from the underlying host. Which of the following patterns can the security analyst use to search the web server logs for evidence of exploitation of that particular vulnerability?

A. /etc/shadow  
B. curl localhost  
C. ; printenv  
D. cat /proc/self/

### 中文完整翻譯

一名 security analyst 發現一個 LFI (Local File Inclusion，本機檔案包含) 漏洞，可以被利用來從底層 host 擷取 credential。下列哪一種 pattern 最適合用來搜尋 Web Server log，以找出這個特定漏洞曾被利用的證據？

A. /etc/shadow  
B. curl localhost  
C. ; printenv  
D. cat /proc/self/

---

### 答案與解析

**正確答案：A. /etc/shadow**

#### 為什麼正確

LFI 的核心是讓 application 讀取 server 本機檔案。

在 Linux 中，/etc/shadow 包含 local account password hash 與 credential-related information，正常 Web request 幾乎不應該要求 application 存取它。

因此如果 vulnerable parameter 被利用，log 中可能出現對 /etc/shadow 的 traversal request。

這和題目描述「透過 LFI 擷取 credential」直接吻合。

#### 其他選項為什麼不對

**B. curl localhost**  
比較像 SSRF (Server-Side Request Forgery，伺服器端請求偽造) 或 command execution 後對 localhost service 發 request 的跡象，不是典型 LFI file target。

**C. ; printenv**  
分號接 shell command 更像 OS (Operating System，作業系統) command injection。

**D. cat /proc/self/**  
/proc/self/ 確實與 Linux process artifact 有關，但 cat 本身是 shell command。如果 HTTP parameter 裡出現 cat，更像 command injection，而不是純 LFI。

#### CySA / 實務概念

LFI 常見 log pattern 包括：

- ../
- URL-encoded traversal
- sensitive local paths
- wrapper / special path abuse
- repeated path-depth guessing

但 detection 不應只搜一個 literal string，因為 attacker 可以使用：

- URL encode
- double encode
- mixed slash
- alternate path
- application-specific path manipulation

因此 analyst 應從 path traversal primitive 出發，而不是只維護單一字串 IOC (Indicator of Compromise，入侵指標)。

#### SOC / IR 記憶點

**看到敏感路徑只是 IOC；真正要理解的是 attack primitive：user-controlled path 逃出預期目錄後，讓 application 讀到本機不該暴露的檔案。**
